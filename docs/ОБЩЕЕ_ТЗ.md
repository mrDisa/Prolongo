## 1. Что строим (коротко)

**Prolongo** — полноценный веб-сервис (не сайт-визитка): внутренняя аналитическая панель для маркетологов хостинга. Она отвечает на три вопроса кейса:

1. **Кому нужно внимание** — рейтинг клиентов по risk-score 0–100, уровни `high` / `medium` / `low` и «нет оценки».
2. **Почему** — у каждого клиента список причин с вкладом в баллах («+45 услуга ждёт оплаты, до удаления 2 дня»).
3. **Сколько потеряем** — ожидаемые потери реальных денег в евро за горизонт (по умолчанию 30 дней) по клиенту и в сумме.

Состав: React-панель + Go-ядро (расчёт, API, live-обновления, метрики, авторизация) + Django-сервис данных (схема БД, загрузка снимков, события, история, симулятор, админка) + PostgreSQL + Prometheus. Запуск — `docker compose up`.

Почему выиграем:
- **Объяснимая модель** (баллы, как в кредитном скоринге) — каждую цифру можно показать жюри.
- **Сортировка по деньгам**, а не по score: клиент с score 65 и €500/мес важнее клиента с score 90 и €2/мес.
- **Расширяемость на деле**: новый признак = один файл в Go, в настройках UI он появляется сам.
- **Любое изменение данных ловится триггерами Postgres** — из админки, через API, напрямую SQL-ом. Это наш ответ на «данные поступают в реальном времени произвольным способом».
- **Система сама копит историю смен статусов** → график «факт / прогноз» и путь к калибровке модели.

Объём: **10 аккаунтов, 30 услуг, 100 транзакций**. Данные синтетические, опорная дата **2026-10-19T15:00:00.000Z**, статусы со временем не меняются.

### 2.2 Схема (точно как в `001_schema.up.sql`)

Имена полей в camelCase, в SQL их нужно писать в двойных кавычках: `"ownerId"`, `"expiresAt"`.

**accounts**

| Поле | Тип | Смысл |
| --- | --- | --- |
| id | bigint PK | |
| email | text unique | `user-0001@example.test` |
| balance | bigint ≥ 0, евроценты | Основной баланс, реальные деньги |
| withdrawBalance | bigint ≥ 0 | Реферальные деньги, доступные к выводу. В данных всегда ≤ balance — считаем частью balance |
| totalReplenished | bigint ≥ 0 | Сколько клиент пополнил за всё время. В данных ≥ balance |
| bonusBalance | bigint ≥ 0 | Бонусы за промокоды и акции. Не выручка бизнеса |
| bonusState | text: `locked` / `unlocked` | Можно ли тратить бонусы (`unlocked` = можно) |

**services**

| Поле | Тип | Смысл |
| --- | --- | --- |
| id | bigint PK | |
| name | text `^[A-Za-z0-9-]+$` | `service-0001` |
| ownerId | bigint → accounts.id | Владелец |
| paymentTerm | `hour` / `week` / `month` / `quarter_year` / `half_year` / `year` | Период оплаты |
| autoProlong | boolean | Автопродление |
| createdAt | timestamptz(3) | |
| expiresAt | timestamptz(3), ≥ createdAt | Конец оплаченного периода |
| status | `active` / `blocked` / `deleted` / `suspended` / `prolong_wait` | |
| price | bigint ≥ 0, евроценты | Цена за один период |

**transactions**

| Поле | Тип | Смысл |
| --- | --- | --- |
| id | bigint PK | |
| amount | integer 0..1000 | Сумма. В данных **не связана с price** — для денег не используем |
| status | `performed` / `not_performed` | Выполнена / не оплачена |
| performedAt | timestamptz(3) или null | null только у not_performed |
| createdAt | timestamptz(3) | |
| type | `order` / `prolong` | Новый заказ / продление |
| serviceId | bigint → services.id | **Связи с аккаунтом напрямую нет**: аккаунт = services.ownerId |

### 2.3 Статусы услуг и как мы их трактуем

| Статус | Смысл по кейсу | Для модели |
| --- | --- | --- |
| active | Работает, деньги идут | Живая, считаем риск |
| suspended | Сервер выключен клиентом, деньги идут | Живая, признак потери интереса |
| prolong_wait | Срок истёк, 5 дней ждём оплату, потом deleted | Живая, самый сильный сигнал |
| deleted | Удалена за неуплату или клиентом | Ушла: факт оттока |
| blocked | Заблокирована, продлить нельзя | Исключаем: маркетинг не поможет |

**«Живые» услуги** = `active`, `suspended`, `prolong_wait`.

### 2.4 Особенности данных, которые надо учесть (проверено по файлам)

1. **Опорная дата в прошлом.** Все даты отсчитаны от 2026-10-19 15:00 UTC. Если считать от реального «сейчас», почасовые услуги давно истекли. Поэтому в системе есть настройка часов: `data` (по умолчанию — «сейчас» = самая поздняя дата в данных), `real` (системное время), `fixed` (заданная дата).
2. **У трёх услуг одного аккаунта одинаковый статус.** Генератор раздаёт статусы по кругу (`(i-1) % 5`), а владельцев — `(i-1) % 10`. В итоге аккаунты 1 и 6 — все услуги active, 2 и 7 — blocked, 3 и 8 — deleted, 4 и 9 — suspended, 5 и 10 — prolong_wait. Значит, 4 из 10 клиентов получат «нет оценки» — хорошо для демонстрации этого требования.
3. **Услуги в prolong_wait истекли месяцы назад** (например, expiresAt = 2026-03-14), хотя по правилам через 5 дней они должны стать deleted. Обрабатываем: если 5 дней прошли — признак на максимуме, причина «срок ожидания оплаты истёк, удаление в любой момент».
4. **Балансы большие относительно цен** (balance до €1000, price до €10), поэтому «не хватает денег» на исходных данных почти не срабатывает. Для наглядности генерируем расширенный набор (кейс это разрешает, см. п. 2.5).
5. **amount не связан с price** — суммы транзакций в деньгах не используем, только факт оплаты / неоплаты.
6. **Дат удаления нет.** Для услуг в deleted оцениваем дату удаления как `expiresAt + 5 дней` (правило prolong_wait) и помечаем её как оценку.

### 2.5 Расширенные данные для демо

- Генератор организаторов: число аккаунтов **не должно делиться на 5**, иначе статусы снова совпадут у всех услуг аккаунта. Пример: `python3 generate.py --accounts 333 --services 1000 --transactions 4000 --seed 7 --out ./generated`.
- Наш генератор `manage.py generate_demo` (Django) добавляет реалистичные сценарии: низкий баланс, выключенное автопродление у скоро истекающих услуг, неоплаченные продления, и историю удалений за 90 дней. Всё, что сгенерировано нами, помечается `source = demo_backfill`, на защите говорим об этом прямо.
- По умолчанию при `docker compose up` загружаются **исходные данные организаторов**. Расширенные — флагом `DEMO_DATA=1`.

## 3. Как это работает

### 3.1 Сценарий маркетолога (он же демо на защите)

1. Вход по логину и паролю (или SSO через OIDC, если успеем).
2. **Обзор**: сколько клиентов в high / medium / low / «нет оценки», ожидаемые потери в €, график «факт / прогноз», топ-10 по ожидаемым потерям.
3. **Клиенты**: таблица — ID, email, баланс, сумма пополнений, score, уровень, потери, топ-причины. Сортировка в обе стороны, фильтр по уровню, поиск.
4. **Карточка клиента**: score и лояльность, вклад каждого признака в баллах, услуги, транзакции, расчёт денег словами, рекомендуемые действия.
5. **Настройки модели**: меняет вес признака или порог → «Сохранить» → за 1–2 секунды без перезагрузки обновляются рейтинг, счётчики и деньги.
6. **Данные**: загрузка снимка, симулятор, лента смен статусов. Любое изменение — панель обновляется сама.

### 3.2 Поток данных

1. Данные меняются любым способом: `PUT /api/v1/source/snapshot`, `POST /api/v1/source/events`, админка Django, симулятор или прямой SQL.
2. **Триггеры PostgreSQL** на таблицах-источниках: запись в `status_events` при смене `services.status` и `pg_notify('data_changed', '')` после любой вставки / изменения / удаления. Postgres склеивает одинаковые уведомления внутри транзакции, поэтому на один снимок приходит одно уведомление.
3. **Go** слушает `LISTEN data_changed`, через 300 мс тишины читает все данные в память и пересчитывает всех клиентов. Также пересчёт по `PATCH /model/settings` и раз в 60 секунд (время идёт, сроки приближаются).
4. Результат — неизменяемый «снимок расчёта» в памяти (`atomic.Pointer`). Из него отдаются API, сортировки и `/metrics`. Раз в пересчёт обновляется строка за сегодня в `core.risk_daily`.
5. Go шлёт по SSE событие `recalculated` → фронт перезапрашивает данные без перезагрузки страницы.
6. Prometheus забирает `/metrics` раз в 15 секунд. Цифры совпадают с панелью, потому что берутся из того же снимка расчёта.

## 4. Модель риска

Баллы, как в кредитном скоринге: признак даёт значение `f` от 0 до 1, оно умножается на вес `w` в баллах, баллы складываются.

```
score(s) = clamp( Σ w_i · f_i(s), 0, 100 )        для каждой живой услуги s
score(a) = max score(s) по живым услугам аккаунта  (внимание нужно, даже если горит одна услуга из пяти)
p(a)     = score(a) / 100                         вероятность непродления — допущение до калибровки
loyalty  = 100 − score
```

Признаки уровня аккаунта (деньги, история платежей) прибавляются к каждой его услуге.

### 4.1 Общие величины

| Величина | Формула |
| --- | --- |
| now | По настройке часов: `data` = `public.source_clock.data_time` — «время источника» (снимок ставит его в самую позднюю дату своих данных, симулятор двигает вперёд; если строки нет — max(services.createdAt, transactions.createdAt, transactions.performedAt)); `real` = системное время; `fixed` = заданная дата |
| H | Горизонт прогноза в днях, настройка, по умолчанию 30 |
| termDays | hour = 1/24, week = 7, month = 30, quarter_year = 91, half_year = 182, year = 365 |
| daysLeft(s) | (expiresAt − now) в днях, может быть отрицательным |
| chargesH(s) | Сколько раз услуга будет оплачена за H дней, если клиент останется: expiresAt > now + H → 0; иначе max(1, ceil((now + H − max(expiresAt, now)) / termDays)). Для prolong_wait и истёкших услуг отсчёт идёт от now |
| needH(a) | Σ price × chargesH по живым услугам — сколько нужно заплатить за H дней |
| funds(a) | balance + (bonusState = unlocked ? bonusBalance : 0) |
| MRR(s) | price × 30 / termDays — месячная выручка услуги |

### 4.2 Признаки (стартовый набор, веса редактируются в панели)

| Ключ | Уровень | f (0–1) | Вес | Текст причины (пример) |
| --- | --- | --- | --- | --- |
| prolong_wait | услуга | status = prolong_wait: graceLeft = 5 + daysLeft; f = clamp(0,6 + 0,4 × (1 − graceLeft / 5), 0,6, 1) | 45 | «service-0005 ждёт оплаты, до удаления 2 дн.» / «срок ожидания оплаты истёк 214 дн. назад» |
| expiring_no_autoprolong | услуга | status ∈ {active, suspended}, autoProlong = false; window = clamp(termDays, 1, 14); daysLeft < 0 → 1; 0 ≤ daysLeft ≤ window → 1 − daysLeft / window; иначе 0 | 30 | «Заканчивается через 3 дн., автопродление выключено» |
| insufficient_funds | аккаунт | needH > 0 → clamp(1 − funds / needH, 0, 1), иначе 0 | 30 | «На балансе €3,00, на продления за 30 дн. нужно €12,00» |
| failed_payments | аккаунт | not_performed / все транзакции услуг аккаунта (0, если транзакций нет) | 10 | «4 из 12 платежей не прошли» |
| churn_history | аккаунт | deleted / все услуги аккаунта | 10 | «Уже удалил 2 из 5 услуг» |
| suspended | услуга | status = suspended → 1 | 8 | «Сервер выключен клиентом» |
| short_billing | услуга | hour → 1, week → 0,5, иначе 0 | 5 | «Почасовая оплата — легко уйти» |
| new_client | аккаунт | MRR(a) > 0 → 1 − min(1, totalReplenished / (3 × MRR(a))), иначе 0 | 7 | «Новый клиент: пополнил меньше чем на 3 месяца» |
| loyal_payer | аккаунт | min(1, успешных prolong / 5) | −10 | «Стабильно продлевает (6 раз)» — снижает риск |

Каждый признак можно выключить (`enabled = false`). Стартовые веса подкручиваем после загрузки расширенных данных: high ≈ 10–20% живых клиентов.

### 4.3 Уровни

| Уровень | Score | Лояльность |
| --- | --- | --- |
| high | ≥ 60 | ≤ 40 |
| medium | 30–59 | 41–70 |
| low | < 30 | > 70 |

Пороги 30 и 60 — тоже настройки модели (medium < high).

### 4.4 «Нет оценки» (`scoreStatus = no_score`)

| noScoreReason | Когда | Текст в UI |
| --- | --- | --- |
| no_services | У аккаунта нет услуг | «Нет данных об услугах» |
| churned | Все услуги deleted (или deleted + blocked) | «Клиент уже ушёл» — считается в факте оттока, не в риске |
| blocked | Все услуги blocked | «Все услуги заблокированы» |

### 4.5 Рекомендации маркетологу

| Признак | Действие |
| --- | --- |
| prolong_wait | Срочно: письмо или звонок со ссылкой на оплату, предложить отсрочку |
| expiring_no_autoprolong | Напомнить о продлении, предложить включить автопродление (бонус за включение) |
| insufficient_funds | Предложить пополнение с бонусом +10% |
| failed_payments | Проверить способ оплаты, помочь с ошибкой платежа |
| churn_history | Опрос о причинах, персональная скидка |
| suspended | Узнать, нужен ли сервер; предложить тариф дешевле |
| short_billing | Предложить помесячную оплату со скидкой |
| new_client | Онбординг: письмо с инструкциями, проверка настройки |

Показываем действия для признаков с вкладом ≥ 5 баллов, по убыванию вклада.

### 4.6 Честно для жюри

Истории в данных нет, поэтому обучать ML не на чем — выбрали прозрачную баллальную модель. p = score / 100 — допущение. Система с первого дня пишет `status_events`; через месяц можно обучить логистическую регрессию на тех же признаках и заменить веса калиброванными.

## 5. Денежная оценка

```
RevenueH(a) = needH(a)                              сколько живые услуги принесли бы за H дней (стоимость услуг)
Bonus(a)    = bonusState = unlocked ? bonusBalance : 0   оплата бонусами — не выручка
Covered(a)  = min(balance, Σ price × chargesH по услугам с autoProlong = true)   спишется автоматически (балансы)
AtRisk(a)   = max(0, RevenueH − Bonus − Covered)
ExpectedLoss(a) = p(a) × AtRisk(a)                   риск
```

| Показатель на Обзоре | Формула | Смысл |
| --- | --- | --- |
| Ожидаемые потери, € | Σ ExpectedLoss | Реалистичные потери за H дней |
| Потери в худшем случае, € | Σ AtRisk по клиентам high | Если уйдут все клиенты высокого риска |
| MRR под риском, €/мес | Σ MRR клиентов medium + high | Доля ежемесячной выручки под угрозой |
| Можно спасти, € | Σ ExpectedLoss топ-20 клиентов | Сколько вернём, если отработать только их |

Пример текста в карточке: «Услуги принесут €10,00 за 30 дней. €2,00 покроют бонусы, €3,00 спишется с баланса автоматически. Под риском €5,00, вероятность ухода 72% → ожидаемые потери €3,60».

Рейтинг по умолчанию сортируется по ожидаемым потерям.

## 6. Архитектура

```
Браузер (React SPA)
   │ HTTP + SSE                                   Keycloak (опц., OIDC)
   ▼
web · nginx :8080 — статика React, маршрутизация, auth_request → core
   │ /api/v1/source/*, /admin            │ /api/v1/*, /metrics
   ▼                                     ▼
ingest · Django + DRF :8001         core · Go :8000  ◄── Prometheus (bearer-токен) ◄── Grafana (опц.)
   │ запись (триггеры → NOTIFY)          │ чтение + LISTEN
   ▼                                     ▼
PostgreSQL 16 — public: accounts, services, transactions, status_events, ingest_batches, source_clock, simulator_state (Django)
                core:   users, sessions, model_settings, risk_daily (Go)
```

| Слой | Технология | Почему |
| --- | --- | --- |
| core | Go 1.26, chi, pgx/v5, goose, prometheus/client_golang | Быстрый пересчёт в памяти, горутины для SSE и LISTEN, нативные метрики |
| ingest | Python 3.12, Django 5, DRF, drf-spectacular | ORM, валидация, админка из коробки |
| web | React 18, TypeScript, Vite, TanStack Query / Table, Tailwind, shadcn/ui, Recharts | Быстрый путь к аккуратной панели |
| БД | PostgreSQL 16 | Транзакции, jsonb, триггеры, LISTEN/NOTIFY вместо брокера |
| Live | Server-Sent Events | Поток сервер → браузер, проще WebSocket, автопереподключение |
| Шлюз | nginx | Один порт и домен (cookie без CORS), `auth_request` |
| Мониторинг | Prometheus (+ Grafana опц.) | Показывает, что `/metrics` реально собирается |
| OIDC (бонус) | Keycloak с импортом realm | Поднимается в compose без внешних сервисов |

**Владение схемой:** схему `public` создаёт и мигрирует только Django (исходные таблицы — дословно `001_schema.up.sql`). Схему `core` — только Go (goose). Конфликтов миграций нет.

**Запасной план:** если к 8-му часу связка не заработала, `PUT /snapshot` переезжает в Go, Django остаётся симулятором и админкой.

### 7.2 Общие договорённости

- JSON, поля camelCase, даты ISO 8601 UTC с `Z`.
- Деньги — целые евроценты, поле с суффиксом `Cents`. Фронт форматирует сам: `€1 234,56`.
- Ошибки: `{"error": {"code": "validation_error", "message": "...", "details": {...}}}`. Коды: 400 bad_request, 401 unauthorized, 404 not_found, 422 validation_error, 500 internal.
- Сортировка: при равенстве — по id asc; клиенты без оценки — всегда в конце при сортировке по riskScore / expectedLoss.
- **Горизонт на лету:** `GET /customers`, `/customers/{id}`, `/analytics/summary`, `/analytics/churn-timeline` принимают необязательный `horizonDays` (1..365). Без него — горизонт из настроек. С ним — расчёт с этим горизонтом при текущих весах, настройки не меняются. Так работает переключатель периода 7 / 14 / 30 / 60 / 90 / «Свой» на обзоре.

- Django не зависит от Go, кроме `/internal/auth/verify` (до его готовности nginx можно запускать без `auth_request`).

## 9. План по времени (24 ч; при 36–48 ч фазы растягиваются пропорционально)

| Фаза | Часы | Go | Django | Frontend | Контрольная точка |
| --- | --- | --- | --- | --- | --- |
| Старт | 0–1,5 | Вместе: разбор данных, `openapi.yml`, схема, репо, скелет compose | | | Контракт и схема зафиксированы |
| MVP | 1,5–8 | Авторизация, движок + признаки, customers, summary | Схема + триггеры, load_dataset, PUT snapshot, compose + nginx | Каркас, логин, таблица клиентов, карточка (моки) | Сквозной прогон в compose на реальных данных |
| Обязательное | 8–14 | Settings + пересчёт, SSE, /metrics, Swagger | POST events, админка, Prometheus, README: запуск | Обзор, настройки, live-обновления, всё на API | **Весь чек-лист приёмки выполнен** |
| Бонусы | 14–20 | churn-timeline, OIDC, тесты движка | Симулятор, демо-данные, тесты | График факт / прогноз, страница «Данные», полировка | Чистый клон запускается по README |

Правила:
- Созвон раз в 2 часа на 5 минут: сделал / дальше / где застрял.
- Застрял больше 30 минут — сразу пишешь в чат.
- Отстаём — режем в порядке: Grafana → OIDC → симулятор → страница «Данные» → график оттока. Обязательное не режем никогда.

## 11. Сценарий защиты (5–7 минут)

1. **Проблема (30 с).** «N клиентов, €X/мес выручки под риском. Маркетолог не знает, кому звонить первым».
2. **Вход + Обзор (1 мин).** Счётчики по уровням, ожидаемые потери, график факт / прогноз.
3. **Найти клиента (1 мин).** Рейтинг → сортировка → карточка из топа: причины в баллах, объяснение денег, рекомендации.
4. **Поменять данные (1 мин).** В админке или через Swagger пополнить баланс → причина исчезает, score падает, панель обновилась сама.
5. **Поменять коэффициент (1 мин).** Усилить «автопродление выключено» → «было → стало». Показать `/metrics` и Prometheus — те же цифры.
6. **Расширяемость (1 мин).** Файл признака на 30 строк, и он сам появился в настройках. Схема архитектуры.
7. **Честность модели (30 с).** «Истории нет → объяснимые баллы. Система уже копит смены статусов — через месяц калибруем веса».

Перед защитой: прогнать сценарий дважды, записать запасное видео, заранее выбрать клиента для демо.
